# XUYI 统一内容、翻译与媒体发布标准

生效日期：2026-11-05  
级别：P0，适用于人工、AI、localGPT、脚本、GitHub Actions、CMS 管理后台和后续所有自动化。

## 1. 先确定唯一真源

| 内容 | 唯一写入位置 | 禁止作为发布源 |
|---|---|---|
| 产品标题、H1、描述、OG、正文、翻译、博客、评价 | Cloudflare D1 / XUYI CMS 正式记录 | dist、线上 HTML、临时 JSON、一次性 HTML 替换 |
| 图片、封面、ALT 对应媒体 | Cloudflare R2；ALT 和引用关系写入 D1 | 直接替换网页图片地址、把本地文件当线上媒体 |
| 模板、组件、渲染器、回归测试、发布规则 | GitHub 源码 | 直接改生成页面 |
| dist、sitemap、静态页面 | 标准构建产物 | 手工修改后再发布 |

业务数据必须进入 D1；媒体必须先进入 R2，再由 D1 记录引用、ALT、语言和发布版本。源码模板可以在 GitHub 修改，但不能用源码里的临时内容绕过 D1 已有人工值。

## 2. AI 和工具的硬规则

- AI 只能做草稿、翻译初稿、SEO 组合建议、去重、格式整理、风险筛查和审计；不能凭空补造容量、材质、认证、MOQ、工厂证据、客户体验、评价或图片事实。
- AI 生成的产品、博客、翻译和评价，必须先进入“待审核”状态；审核通过后才能条件写入 D1。评价必须有可核验来源、准确 SKU、fingerprint、source 和审核状态。
- 工具默认只读或 dry-run。实际写入必须使用现有、已鉴权的 XUYI D1/CMS 或 R2 管理入口，并明确记录操作者、批次、时间、旧值摘要、新值摘要和 publish revision。
- 禁止脚本、插件、自动化或 AI 直接写 dist、线上 HTML、Cloudflare Pages 成品或 R2 缓存来冒充发布。禁止用旧静态回退表覆盖后台编辑。
- 工具必须幂等：重复运行不重复插入、不删除已有数据、不回退人工修改；更新必须按资源 ID、语言、SKU 和旧值/指纹条件写入。条件不满足就停止并报告，不强制覆盖。
- 任何计费、额度、试用赠金或费用不明确的 API 禁止使用；只用项目已批准且可确认安全的连接。

## 3. 产品、博客、评价和图片发布顺序

1. 读取 D1/CMS 当前记录、字段所有者和 publish revision，先做可恢复快照。
2. 读取真实产品/文章/评价来源，生成待审核草稿；翻译必须逐语言检查，不用英文正文自动充当译文。
3. 人工确认事实、SEO、五语、链接和图片场景。博客正文放 2–5 个真实相关产品链接，结尾人工选择 2–3 篇相关阅读。
4. 新图片先校验来源、尺寸、格式、SHA-256 和场景，再上传 R2 新对象；R2 成功后才写 D1 图片路径、ALT、语言和引用。原对象不覆盖、不删除，除非通过引用检查和可恢复流程。
5. 对 D1 做条件写入并 bump publish revision；失败或版本冲突时停止，不自动重试覆盖。
6. 由标准构建从 D1 + R2 + GitHub 模板生成 dist；必须完成两次干净构建、回归测试和 CMS owner-edit 保留测试。
7. 通过 CI 后才部署；部署后核对 build SHA、D1 revision、R2 对象、代表页面和 sitemap。失败停在 CI，不发布临时产物。

## 4. 已发布语种翻译审计门禁

当前生产基线为 EN、ES、PT、RU、TR；实际检查集合始终以 D1 `language_config` 中 `enabled + publishReady` 的语种为准。每个资源发布前必须检查：

- html lang、title、H1、meta description、OG、正文、导航、分类、按钮、ALT、FAQ、JSON-LD 的可见文案与目标语言一致。
- 不得出现整句英文回退、旧语言目录、英文面包屑、英文分类侧栏或“只翻标题不翻正文”。OEM、ODM、B2B、MOQ、SKU、ml、oz、FAQ 等行业缩写和型号可以保留。
- 每个语言 URL 的 canonical、hreflang、sitemap 和内部链接必须指向同语言已发布页面；缺翻译时不生成假翻译链接。
- 发生一条高置信度漏翻译，就阻止该资源批次发布，进入 D1/CMS 翻译队列；禁止在构建后替换 HTML 规避门禁。

2026-11-05 线上只读审计结果：sitemap 1,812 个 URL，HTTP 错误 0，五语 html lang 错误 0。发现并已在共享模板修复 24 个多语分类侧栏英文回退、4 个 About 面包屑 Home；另有 9 个博客多语正文/相关阅读含英文片段，属于 D1/CMS 内容，必须按本标准回写 D1 后再复核，不能直接改成品文件。FAQ、OEM/ODM 和 Email 等上下文词未自动判定为漏翻译。

## 5. SEO + GEO 内容可引用性标准（2026-11-10，永久执行）

本项目不把 GEO 视为一个单一、固定、公开的 AI 算法；GEO 的执行目标是让搜索引擎和 AI 系统能够理解、验证并引用页面内容。所有新写、重写或发布的产品、Blog、FAQ 和普通页面，必须先满足 SEO 基础，再按以下规则提高内容的可引用性。

### 标题、导航和页面结构

- 标题优先采用句子式、口语化、提问式表达，覆盖明确的长尾搜索意图和常见 FAQ；避免所有页面复用同一句营销标题。
- 页面导航清晰、层级扁平、分类和面包屑稳定；产品、分类、Blog、FAQ 和关键服务页之间保持真实、可理解的内部链接。
- H1、Title、Meta Description、正文、FAQ 和结构化数据必须相互一致，目标语言页面不能用英文内容冒充翻译。

### 内容深度、事实和证据

- 内容先直接回答问题，再解释参数、判断条件、操作步骤、适用范围和风险边界；避免“优质、领先、快速、专业”等没有证据的营销形容词。
- 优先使用参数清单、对比表、选型逻辑、决策树、检查表和 FAQ。标题示例可以是“液压油滤芯选型需要确认的 6 个参数”“原厂滤芯平替前必须核对的 5 个条件”，但实际数字必须与正文和来源一致。
- 可以写真实案例、实操过程图、数据验证、第三方测评、客户好评截图和实际使用场景，但必须有可核验来源、授权或明确的示意图声明。类似“能耗降低 30%”“交付周期 7 天”“通过 ISO 9001”等事实，只有在项目来源、D1/CMS 记录或可核验第三方资料支持时才能发布。
- 产品、品牌和厂家信息应在回答采购问题时自然出现，不为了品牌提及强行插入；产品参数、材质、容量、认证、MOQ、交期、工厂证据和客户关系不得由 AI 猜测。
- AI 可以提高研究、组织、翻译和审计效率，但不得批量生成无原创价值、空泛重复或未经核验的内容。每篇文章必须有独立问题、独立证据、独立采购场景和明确的读者下一步。

### 数据库、图片和外部平台

- 正文、Title、Meta、翻译、内链、FAQ、评价和产品数据仍必须写入 D1/CMS；图片先核验后进入 R2，再由 D1 保存路径、ALT、语言和引用关系。
- 图片优先使用真实产品/使用场景、操作过程图、对比图或清楚标注的示意图；不得用虚构客户、工厂、订单、测试或认证作为 AI 内容的“证据”。
- Reddit、Quora、YouTube、LinkedIn 和行业论坛属于后续分发渠道，不是默认发布源。获得明确授权后，按平台改写为问答、视频脚本、案例帖或专业帖子，不直接复制整篇文章群发；分发内容仍应回溯到网站 D1/CMS 的事实源，避免重复、误导和垃圾外链。

该标准适用于人工、AI、localGPT、脚本和 GitHub Actions。后续收到“发布文章”任务时，默认按本节执行，不再要求用户重复说明；若缺少来源证据，保留为待审核而不是补造事实发布。

## 6. 回滚和交接

- 文本回滚使用 D1 旧版本/快照或 CMS 审计记录；媒体回滚使用旧 R2 对象和 D1 引用恢复；源码回滚使用 Git 提交，禁止用旧 dist 覆盖现状。
- 每次发布交接必须写明：D1 表/资源/语言、R2 对象和 SHA、Git 提交、构建/部署 run、测试结果、线上核验 URL、是否存在待处理翻译。
- 未完成 D1/R2 写入、翻译审核、双构建或线上核验时，状态只能写“草稿/待审核/未发布”，不能写“已完成”。

本文件是产品、博客、评价、翻译、图片、SEO/GEO 和 AI/工具发布的统一操作标准；与历史脚本或旧说明冲突时，以本文件、AGENTS.md 和 PROJECT_CHANGE_POLICY.md 为准。

## 7. 2026-11-11 发布入口与后台维护收口

- Blog 批量发布只使用 `/api/admin/blog-batch` 一个通用入口。入口先读取 D1 `language_config`，以 `enabled + publishReady` 的语种集合生成翻译页和列表卡片网格；不得在接口或工作流里写死语种数量、日期接口或旧批次数量。
- 批量重跑采用“已存在且完全相同则复用，已存在但内容不同则 409 停止”的条件策略。任何 D1 人工编辑都不能被旧批次覆盖；旧日期命名的批量 CI 写入口已经 fail-closed，只保留历史源码和离线回归资料。
- Blog 列表重排必须读取完整 D1 `published` 顺序，只调整每张完整卡片的位置；历史嵌套卡片可由共享解析器恢复，但禁止通过改线上 HTML 或 dist 解决。
- 定时发布的多语队列表不再使用固定语种 CHECK；初始化时会把旧表迁移到配置驱动结构。发布器检查 `locales.length`，不允许使用固定 `4` 或固定语种数组作为完成条件。
- 后台模块 06/产品 SEO/媒体 ALT 的语种选项、产品记录和数量均由 D1 API 返回；界面不得显示旧的“五语”“101 个产品”等事实性固定数字。批量导入的单次安全上限如果存在，必须明确标注为“单次批次上限”，不能冒充全站产品总数。
- 发布完成的最小回归集：全量 JS/Python 语法、preflight、P0 真源门禁、CMS owner 优先、Blog 列表单卡片与 D1 顺序、动态语种授权、语言切换 failover、代表 Blog 运行时和第二次干净构建。缺少 D1 snapshot 时，构建不得伪造成功；只能报告等待受鉴权快照。
