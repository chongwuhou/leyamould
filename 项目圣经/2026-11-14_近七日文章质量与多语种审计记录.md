## 根因

1. 批量发布时，英文正文和多语种正文采用了两套深度：英文有完整章节，多语种只写入短的 `details`/摘要段落。
2. 多语种翻译保存接口只检查了 HTML 是否存在、状态是否可发布，没有检查每个章节的实际正文长度、FAQ 数量和源文对应关系。
3. 旧批量模板允许 5/6/9 个章节、3 个 FAQ 等历史结构继续发布，后续人工检查只看页面能否打开，没有检查内容是否具有采购决策价值。
4. 发布后只验证了数据库写入，未把 D1 修订、静态构建版本和线上页面正文放进同一条门禁链路，所以会出现“数据库已更新，线上仍是旧静态内容”的错觉。

## 固定门禁

### 内容

- 新文章英文源文至少 7 个实质章节；每章必须有针对主题的采购动作、判断条件、风险边界或验收记录。
- 至少 4 个 FAQ、8 个采购检查项、2–5 个真实产品内链和 3 个相关文章。
- 标题、Meta Description、H1、摘要、章节和 FAQ 必须围绕具体长尾问题，不能用同一套泛化文案。
- 禁止只写“高质量、快速交付、支持定制”等不可核验形容词；必须写清要确认的型号、容量 ml/oz、材质、颜色、包装、样品和验收条件。

### 多语种

- 每个 D1 配置语种必须有完整独立的正文，不能只保存标题、`details` 短句或英文兜底。
- 多语种章节数量必须与源文对应；每章至少保留一个完整主题段，并包含该文章自己的采购条件、操作步骤或判断标准。
- 保存前检查每个语种的正文总量、章节完整性、FAQ、产品链接、标题和 Meta Description；发现空段、英文片段或短摘要必须阻止发布。
- 多语种页面只能通过 D1/CMS 写入，不能直接编辑静态 HTML。

### 发布与线上核验

1. 先写入 D1/CMS，保留原字段、图片、链接和所有者信息。
2. 写入后读取 D1 revision，提交全站发布队列。
3. GitHub Actions 从模板读取 D1/R2，完成干净构建、第二次构建、校验和 Cloudflare Pages 部署。
4. 只有在 `build-meta.json.publishRevision === /api/publish-state.publishRevision` 时，才算线上发布完成。
5. 每次发布后逐语种检查详情页：HTTP 200、唯一 H1、正文章节、FAQ、产品内链、相关文章、标题、Meta、canonical、hreflang、列表顺序和 sitemap。
6. 文章发布不使用浏览器操作，不调用 Google 翻译 API；人工维护和 AI API 维护都必须执行同一套门禁。
