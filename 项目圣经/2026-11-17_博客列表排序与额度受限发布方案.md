# Blog 列表排序与额度受限发布方案（2026-11-17）

## 结论

Blog 的内容真源仍是 Cloudflare D1/CMS。生产默认生成静态页面；Pages Function 只保留为显式开关 `XUYI_BLOG_RUNTIME_MODE=dynamic` 的备用入口。

## 唯一排序规则

列表和构建快照统一使用：

`ORDER BY COALESCE(published_at, updated_at) DESC, slug ASC`

- 已发布文章按 D1 的实际 `published_at` 从新到旧排列。
- 仅对缺失 `published_at` 的历史记录回退到 `updated_at`。
- 文章正文、翻译、SEO、图片或内链的人工修改不会改变发布时间排序。
- 英文与所有后台配置为 enabled + publishReady 的语种使用同一次 D1 snapshot 的 slug 顺序；只移动完整卡片，不重写卡片内部内容。
- 不改 URL、不改发布日期、不直接编辑 dist/或线上 HTML、不用批次 slug 置顶。

## GitHub Actions 额度受限时

- 不能以 GitHub Actions 失败为理由直接改 D1、dist、Pages 成品或 R2 缓存。
- 文章、翻译、图片仍先写入 D1/R2；排序修复仍先改共享源代码和回归门禁。
- 生产上线可使用项目既有的本机 Wrangler 发布入口，在完成 D1 snapshot、两次干净构建、全站回归和线上验收后执行；不能使用不完整静态上传替代 Pages Functions。
- 若当前机器没有经过授权的 Cloudflare 发布凭据，则保留源码修复和 D1 数据不动，等待额度恢复或由管理员在安全环境执行本机 Wrangler 发布；禁止把令牌贴到聊天或写入仓库。
- GitHub Actions 恢复后，首次发布必须核对生产 build-meta、五语列表数量/slug 集合/顺序、静态模式和 Functions 仍可用。

## 最低回归

每次 Blog 发布或列表修复都必须检查：

1. D1 published 文章数量、slug 集合无丢失/重复。
2. 五语（或后台实际 publishReady 语种）列表使用同一 slug 顺序。
3. 第一页首项发布日期不早于后续项；发布日期相同时按 slug 稳定排序。
4. 后台人工编辑文章后，列表顺序仍由 published_at 决定。
5. 默认静态模式未被动态 Function 接管。
