# 近期 Bug、返工、回滚与重复修改复盘（2026-11-18）

## 1. 复盘范围与结论

本次复盘覆盖最近一轮博客多语发布、静态构建、Cloudflare Pages 发布、图片替换和列表页修复记录，重点核对 2026-11-17 至 2026-11-18 的 GitHub Actions 失败日志、重复提交、取消运行和线上回归。

结论不是“某一篇文章偶然写错”，而是发布系统存在共同的结构性缺口：

1. 旧的一次性发布入口仍留在正式 workflow，历史修复提交可能再次触发数据写入或重复发布。
2. Pages Function 没有在完整构建前做语法门禁，低级语法错误在耗时构建后才暴露。
3. 渲染器和测试对具体 HTML 形状做精确字符串假设，新文章或后台编辑改变结构后就会误判或无法构建。
4. Blog 卡片存在新旧两种 DOM 契约，但没有把兼容规则和回归测试作为正式组件契约。
5. 共享 CSS 未自动带内容版本，部署成功后浏览器仍可能读取旧 CSS，造成“代码已修、页面未修”的重复排查。
6. 生产队列不取消已被新提交取代的运行，定时任务与人工提交叠加，放大了排队、回滚和重复发布成本。

因此本次不只记录事件，而是把这些根因落成代码门禁、workflow 约束和固定操作手册。

## 2. 已核对的代表性问题

| 类别 | 证据/现象 | 共同根因 | 永久防线 |
| --- | --- | --- | --- |
| 多语 Blog 图片被拉伸 | 旧卡片使用 news-card__media，共享样式只覆盖 news-card__image；图片 HTML 高度属性又参与布局 | 新旧 DOM 契约没有统一 | 保留兼容 CSS；新增 Blog 卡片契约测试；正式 renderer 只生成 canonical 结构 |
| 修复后浏览器仍显示旧样式 | shared CSS URL 没有内容版本 | 静态资源缓存策略未纳入发布契约 | renderer 对 CSS 计算内容指纹并追加 ?v=...；测试固定检查 |
| Pages 部署失败 | functions/api/admin/blog-batch.js 曾出现正则转义语法错误 | 没有在 build 前运行 Functions 语法检查 | workflow 在安装构建依赖前运行 scripts/test_pages_functions_syntax.py |
| 新文章构建失败 | 本地化日期更新依赖“恰好一次”字符串匹配；新增正文结构改变后匹配为 0 | 生成 HTML 被当成数据接口，渲染逻辑不具备语义容错 | 日期、作者、标题等从 D1/CMS 字段渲染；测试不再绑定固定文章或固定 HTML 片段 |
| 可信度 SEO 门禁失败 | 技术 SEO 测试对特定本地化作者 URL 作固定断言，新文章没有该固定形态即失败 | 测试假设历史样例，而不是验证通用规则 | 测试按 D1 当前 published 内容和后台语言配置动态验证；新增文章不触发旧样例要求 |
| 媒体发布 403 | Blog 批量发布脚本直接调用媒体入口，权限/路由不匹配时在写入阶段才失败 | 写入前没有把正式 endpoint、授权和幂等性作为 preflight | publisher 只能走一个通用正式入口；先 dry-run/鉴权校验，失败立即停止，不进入后续发布 |
| 列表数量/顺序异常 | 多语列表与英文不同步、旧列表只保留部分卡片 | 列表不是一次 D1 snapshot 的完整结果，且存在历史一次性修复入口 | 统一按 D1 published 快照和同一排序生成；禁止固定总数、日期脚本和发布后 HTML 补丁 |
| 重复运行和回滚成本高 | 同类 Publish/Prepare/Repair 提交密集出现，旧运行仍排队 | 正式入口过多、并发运行不取消 | workflow 只保留 generic publisher；同组运行 cancel-in-progress: true；历史脚本仅作审计档案 |

## 3. 从根本上固定的工程规则

### 3.1 一个正式发布入口

- 内容写入只能经过通用 D1/CMS publisher；图片先进入 R2，再由 D1 保存路径、ALT、语言和引用关系。
- 带日期的批处理脚本、一次性修复 endpoint 和按提交信息触发的发布步骤只保留作历史审计，不能出现在生产 workflow。
- 任何新入口必须同时补充：字段所有者、幂等条件、失败行为、回滚方式、回归测试和线上验收；否则不允许接入。

### 3.2 先验证能否发布，再构建，再部署

固定顺序：

1. 读取 AGENTS、PROJECT_CHANGE_POLICY、项目圣经和统一执行手册。
2. 先跑 Pages Functions 语法检查和源隔离检查。
3. 读取 D1/CMS 当前值，确认语言、状态、媒体引用和 owner 编辑优先级。
4. 再做完整构建、第二次干净构建和回归测试。
5. 所有门禁通过后才允许 Cloudflare Pages 部署；任何失败都停在 CI，禁止用 dist、线上 HTML 或缓存补丁补发布。

### 3.3 渲染器按语义工作，不按历史 HTML 猜测

- 文章日期、作者、SEO、正文、FAQ、Breadcrumb、keywords、图片属性和列表排序都必须从 D1/CMS 或配置读取。
- 禁止用某个旧片段必须出现一次、某个历史 URL 必须固定存在作为通用发布逻辑。
- 测试应验证不变量：字段所有权、当前配置语种、slug 集合、唯一 H1、canonical/hreflang、链接和媒体引用；不验证偶然的旧文案。

### 3.4 组件契约必须覆盖新旧数据

- 共享组件有新旧 DOM 结构时，要么完成正式迁移，要么明确保留兼容样式和测试；不能只修当前模板而忽略 D1 中已存在的 owner 内容。
- Blog 卡片图片必须有受支持的 wrapper、固定比例、object-fit: cover，并通过 scripts/test_blog_card_contract.py 门禁。
- 共享 CSS 和 JS 必须由内容指纹或等价版本策略更新，避免浏览器缓存旧资源。

### 3.5 队列、失败和回滚

- 同一生产组只保留最新提交；新提交到来时取消尚未完成的旧运行。
- 失败先分类：语法/测试失败不部署；鉴权/接口失败不重试写入；部署失败只允许重跑已失败步骤，不能重复执行 D1 迁移。
- D1/R2 数据迁移必须条件写入、记录 revision、可重复执行；回滚优先恢复已知稳定源代码并重新生成静态站，不直接改线上 HTML，不删除原始 R2 对象。
- 回滚前先保存当前 commit、publish revision、D1/R2 变更记录；不得用旧 dist 覆盖新的 CMS 数据。
