# LEYA MOULD 统一执行手册（人工 + 任意 AI）

版本：2026-11-24
适用仓库：`chongwuhou/leyamould`
生产站点：`https://leyamould.com`
统一时区：Asia/Shanghai

本手册把水杯项目已经验证的工程原则转换为 LEYA MOULD 的执行规则。它只约束本仓库，水杯项目全程只读。前台视觉模板已经冻结；后续工作优先放在 D1/CMS、R2、共享渲染器、测试和发布链路，不通过生成后的 HTML 打补丁。

## 1. 四个真源

| 内容 | 唯一真源 | 验收方式 |
| --- | --- | --- |
| 品牌、导航、页面正文、产品/型号、Blog/News、视频、翻译、SEO、发布状态 | LEYA Cloudflare D1/CMS | 读取 snapshot、字段所有者和 publish revision |
| 图片、PDF 和媒体对象 | LEYA Cloudflare R2 | HEAD、MIME、大小、SHA、ALT 和引用关系 |
| 模板、Functions、构建器、测试和工作流 | 本 GitHub 仓库 | 两次干净构建、CI、源码审查 |
| 静态页面、sitemap、build-meta | 标准构建产物 | 线上 revision、路由、canonical/hreflang、媒体回读 |

`dist/`、线上 HTML、浏览器缓存、聊天记录和临时 JSON 只能用于诊断，不能作为发布源。数量、语种、排序和公开状态不能写死为历史数字。

## 2. 先判定任务边界

1. **只读审核**：读取仓库、D1/CMS、R2、构建或线上页面，不写任何外部状态。
2. **内容任务**：先建立审核草稿，再通过正式后台/API 条件写入 D1；图片先进入 R2，再把路径、ALT、语言和引用关系写入 D1。
3. **模板/代码任务**：修改共享模板、Functions、构建器或回归测试；禁止逐页编辑生成 HTML。
4. **发布任务**：仅在用户明确授权后触发 GitHub/Pages/Cloudflare 发布，完成 CI、build-meta、revision、路由和媒体回读。

任何不清楚的事实（钢材、穴数、机台接口、认证、MOQ、交期、客户、订单、人物或实拍关系）保持空白或标记“需确认”，不能用推测填充。

## 3. 标准写入顺序

1. 读取当前 D1/CMS 快照、启用且 `publishReady` 的语言、字段更新时间、发布状态和 revision。
2. 对本批内容做事实来源、重复主题、关键词蚕食、内链和语言完整性审计。
3. 生成待审核内容：产品族/型号、页面、News/Blog、YouTube 视频或评价分别使用各自模块字段。
4. 对每张图片或 PDF 记录来源、可见内容、授权边界、尺寸、MIME、压缩结果、SHA 和 ALT；R2 成功后再写 D1 引用。
5. 使用正式后台或已鉴权 HTTPS API 条件写入。相同内容重跑必须幂等；冲突返回 409 时停止，不覆盖人工修改。
6. 重新读取 D1/R2，核对写入数量、语言集合、引用对象和 publish revision。
7. 从最新 snapshot 做两次干净构建，运行语法、路由、模板、多语、SEO、媒体、数据真源和隔离测试。
8. CI/Pages 完成后回读 `build-meta.json`、`r2-usage-index.json`、代表列表/详情页、canonical、hreflang、OG、sitemap 和媒体 HTTP 状态。

没有 D1/R2、CI、revision 和线上 URL 的完整证据，只能报告“草稿/待构建/待验证”，不能报告“已发布”。

## 4. LEYA 内容模块门禁

### 型号参考库和产品族

- `leya_model_references` 是独立模块；HMould 或其他站点的条目只能作为“资料参考”，不能自动变成 LEYA 已交付 SKU、能力承诺或客户案例。
- 每条记录需要稳定 slug、产品族、英文标题/ALT、来源、说明、排序、审核状态和语言字段；公开记录必须有 LEYA R2 `/media/` 对象。
- 资料缺少钢材、穴数、尺寸、机台、认证或交付证据时，卡片只展示已核实信息并引导询盘。
- 删除已发布记录前先撤回并保留可回滚快照；新增记录不得因为旧页面数量门禁失败。

### News/Blog

- 一个页面只服务一个明确的采购问题或工程主题；正文、FAQ、CTA、产品内链和相关阅读必须有真实来源。
- 文章正文自然放入 2–5 个相关已发布产品/型号详情链接，结尾由人工挑选 2–3 篇直接相关的已发布文章；不使用导航、页脚或自动推荐冒充编辑内链。
- 标题、H1、Meta、OG、首段、章节、FAQ 和翻译都以 D1 最终字段为准。文章列表统一按 D1 `COALESCE(published_at, updated_at) DESC, slug ASC` 排序。
- 当前没有真实资料时保持草稿，不用通用图片、虚构客户、虚构认证或 AI 生成的“实拍”替代证据。

### YouTube 视频

- 后台只保存经确认的 YouTube URL、标题、多语标题/描述、发布时间、分类、缩略图和公开状态。
- 列表发布时间使用后台字段；URL 无效、视频下架或语言字段不完整时不发布，先停在草稿。
- 删除/编辑通过视频模块 API 完成，不能直接改生成页面；公开列表和详情页必须从同一 D1 snapshot 构建。

### 评价和案例

- 只发布有来源、授权和可核验身份/项目关系的评价或案例；未核实文本只能标记为示意，不能冒充客户原话。
- 不为填充版面生成星级、公司、国家、交付结果、订单或项目参数。图片不得冒充真实客户/工厂/型号证据。

## 5. 多语、SEO 与 GEO 审计

- 语种集合始终读取 D1 `language_config` 的 `enabled + publishReady`；当前公开语言以线上配置为准，不能在代码里写死语言数量。
- 每个公开语言都必须有独立 Title、H1、Meta、OG、正文、章节、FAQ、面包屑、按钮、ALT、canonical、hreflang 和结构化数据；缺翻译就停止该语言发布，不用英文冒充完成。
- 语言列表使用同一份 D1 已发布 slug 集合和排序；发现缺卡、重复卡、额外卡或跨语串文，停止发布并回写正式字段。
- GEO 内容先直接回答买家问题，再给参数、判断条件、适用边界、证据来源和询盘下一步；没有来源的数字、认证和交付承诺明确标为待确认。

## 6. 媒体标准

- 上传前实际查看最终图，确认主体、场景、清晰度、无水印/错位/白底误用，并记录来源和授权边界。
- 图片优先 WebP，按用途压缩；Blog 封面默认 1200×800、3:2、30–350KB，产品图按展示清晰度和 R2 体积共同审核。不得只改文件名或扩展名冒充压缩。
- 每个媒体对象保存 SHA、MIME、尺寸、大小、ALT、语言和引用记录。后台替换的图片优先于旧静态回退。
- R2/D1 响应不明确时先 HEAD/查询确认是否已写入，再决定是否重试；禁止盲目重复上传。

## 7. 构建、发布和回滚

- 代码改动：先本地测试，再提交主分支；构建器从干净目录读取 D1 snapshot，不能依赖旧 `dist`。
- 内容改动：先 D1/R2 回读，再双构建；不要通过提交信息、日期文件或一次性脚本隐式写业务数据。
- 发布后检查 source revision、publish revision、公开语言、代表页面、sitemap、canonical/hreflang、OG、R2 HTTP 200 和 MIME。
- 模板问题回滚 GitHub 提交；业务数据回滚 D1/R2 的已审核记录；两者不能互相替代。DNS、密钥和其他项目资源不在普通回滚内。
- 发布失败时保留已经确认写入的数据，只修模板/测试/构建；若线上异常，记录 HTTP、revision 和根因后从正式历史重建。

## 8. 完成记录

每次任务至少记录：变更类型、正式真源和字段、审核/来源、D1/R2 回读、测试、两次构建、CI/Pages revision、代表 URL、未完成项和回滚点。任何“看起来成功”的局部页面都不能替代全链路证据。

## 9. 永久禁止

- 修改水杯项目或连接其生产 D1/R2、域名、凭据和业务数据。
- 直接编辑 `dist/`、线上 HTML、Pages 成品或 R2 缓存来冒充修复。
- 编造产品规格、认证、客户、评价、图片事实或 SEO 证据。
- 使用费用、额度、试用赠金或条款不明确的外部 API；不得用 Google API 代替已有正式数据源。
- 在 D1/R2/CI/线上回读未完成前宣称“已上线”或“已收录”。
