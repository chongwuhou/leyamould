# LEYA MOULD 后台模块化与更新流程

## 目标

前台 `templates/site`、`assets/site.css`、`assets/site.js` 和 `mould_build.py` 的版式是冻结的视觉源。后台只负责审核后的业务数据，不直接改写前台 CSS，也不把后台 HTML 当成新的模板。

## 数据真源

- Cloudflare D1：品牌与联系方式、语言配置、导航、页面 SEO、页面正文、模具分类内容、型号参考库 `leya_model_references`、新闻/Blog、YouTube 视频、发布版本号。
- Cloudflare R2：经审核的图片、PDF、视频相关媒体和 ALT 文案。
- GitHub：模板、渲染器、Functions、管理端和测试；不存放生产数据库内容。
- `data/mould-catalog.json`：D1 无快照或字段为空时的安全回退，只包含 LEYA MOULD 模具分类。

## 发布链路

1. 管理后台写入 D1/R2，所有写入经过管理员认证、字段校验和发布版本号递增。
2. GitHub Actions 在构建前调用只读 `/api/build-snapshot`，将当前已发布内容保存为 `_local_ops/build-snapshot.json`。
3. `mould_build.py` 读取快照，覆盖品牌、导航标签、SEO、页面正文、分类内容、型号参考、Banner、新闻和 YouTube 视频；未发布或不合法的数据自动回退到源模板。
4. 运行语法、隔离、路由、模板和双构建测试；通过后才部署 Pages。
5. 第二次重新读取快照并清洁构建，确认构建结果不依赖旧的 `dist` 或旧快照。

## 后台模块边界

品牌/联系方式、语言、导航、页面 SEO、页面正文、模具分类、型号参考库、Blog/News、YouTube 视频、Banner、媒体 ALT、询盘、评价和发布状态均为独立模块。模块之间通过 D1 的明确字段连接，不能借用水杯项目的商品、分类或业务数据。

### 型号参考库的编辑与发布

1. 后台「型号参考库」只保存 D1 草稿或正式记录；批量导入使用离线 `scripts/prepare_model_reference_import.py` 生成的审计 JSON，不在服务端调用第三方目录或翻译 API。
2. 每个正式记录必须绑定 `/media/` R2 图片；R2 对象存在、英文 ALT、来源和语种字段通过校验后才能从 draft 变为 published。
3. 发布会递增 publish revision；构建快照按产品族、排序、slug 确定顺序，静态生成后才进入分类页。删除只允许草稿，已发布记录先撤回并重新构建。
4. 参考卡片仅复用现有询盘入口；如果资料缺少穴数、钢材、机台或交付证据，页面不补写推断值。
### LEYA 系统层、页面正文和审计

- `functions/_shared/leya-system.js` 只维护 LEYA 自有的 schema checkpoint 和共享 `site_state` 表。内容编辑沿用水杯项目的轻量流程：管理员认证、字段校验、D1 保存、publish revision 递增和构建验收。
- 普通页面的英文正文由 `xuyi_page_content` 管理。首次迁移使用仓库内的 `data/mould-page-bodies.json`，只插入缺失记录；已有 D1 编辑永远优先。西班牙语没有对应翻译时继续使用渲染器的西语基线，不把英文正文误套到西语页面。
- 日期命名的旧内容种子地址只保留为关闭的兼容别名；新的 owner-approved 操作统一使用 `/api/admin/content-seed`，避免旧链接在生产环境继续写入 D1。
- 管理后台的普通图片上传和 Blog 封面上传先在浏览器压缩为 WebP（最长边 2400px、质量约 0.88）再进入 R2；替换图片仍保留原文件备份和同路径回滚。

## 安全与回滚

- `functions/_shared/mould-routes.js` 是模具路由和九个分类的写入白名单；旧的 `xuyi-routes.js` 只保留兼容导出，不再接受水杯型号。
- 构建快照只输出模具路由、九个模具分类和公开内容，不输出询盘、密钥或其他私有表。
- 发布失败时不修改线上站点；修正数据后重新递增发布版本并重跑双构建。需要回滚模板时回滚 GitHub 提交，需要回滚业务内容时恢复 D1/R2 的已审核记录。
