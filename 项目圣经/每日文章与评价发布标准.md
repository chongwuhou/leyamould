# XUYI 每日文章与评价发布标准手册

版本：v1.0  
建立日期：2026-11-01  
适用项目：旭一 XUYI 水杯独立站  
仓库：chongwuhou/xuyi-drinkware-site  
生产站点：https://xuyibottles.com  
统一时区：Asia/Shanghai（北京时间）

> 本手册是每天重复执行的唯一操作标准。以后每日发布先按本手册执行，不再临时拼接流程、不再凭记忆找脚本、不因重试重复写入 D1/R2。

## 1. 每日固定任务与数据边界

### 1.1 B2B 文章

每日标准批次：

- 3 篇不同采购场景的 B2B 文章。
- 每篇 5 种语言：英文、 西班牙语、葡萄牙语、俄语、土耳其语。
- 共 15 个详情页；5 个语言 Blog 列表均应出现这 3 篇文章。
- 每篇 1 张独立、经视觉审核的封面图，共 3 张，上传到 Cloudflare R2。
- 文章正文、翻译和列表卡片写入 Cloudflare D1；页面由现有 CMS/模板输出。
- Sitemap 更新后再提交 IndexNow。提交不等于搜索引擎已经收录。

### 1.2 客户评价

评价发布必须区分“常规每日自动任务”和“站长额外指定批次”：

- 常规自动任务：每天北京时间约 09:17，随机发布 1 条真实、未使用过的 Excel 评价。
- 真实评价源：私有文件 review_import_private/101_verified_buyer_reviews.json，对应原始 101 条评价。原始评价、作者、星级、型号映射和 SHA-256 指纹必须保持一致。
- D1 永久追加账本是唯一去重依据；一个型号不能重复发布。即使前台评价被删除，也不能再次使用该型号。
- 额外发布 2、3 或 4 条，只能是站长当天明确批准的一次性批次；不能把某天的特殊数量改成每日默认规则。2026-10-28 的 4 条属于一次性例外，普通 D1 日上限为 3 条。
- 当天已经有评价时，常规任务应自动不再追加；额外批次必须先读取当天账本，再判断能否安全发布。

## 2. 数据真源与职责分工

| 内容 | 正式数据源 | 发布位置 |
|---|---|---|
| 评价原文与型号 | 私有 Excel 来源 JSON | D1 评价表 + 追加账本 |
| 英文 B2B 文章 | data/blog-guides-YYYYMMDD-1/2/3.json | D1 Blog CMS |
| 四语译文 | data/blog-localized-copy-YYYYMMDD-1/2/3.json | D1 Blog 翻译表 |
| 封面审核与 SHA | data/blog-images-reviewed-YYYYMMDD.json、data/blog-cover-editorial-approvals.json | R2 |
| 页面布局 | 共享模板、functions/blog、functions/_shared/blog-cms.js | Cloudflare Pages |
| Sitemap / IndexNow | 正式 sitemap 生成与提交流程 | 生产站点 / IndexNow |

禁止把临时 dist 文件、手工改线上 HTML 或浏览器缓存当作正式数据源。后台 D1/CMS 的人工修改优先于旧脚本和历史默认值。

## 3. 客户评价发布标准流程

### 3.1 常规每日自动发布

固定工作流：

- 工作流：.github/workflows/publish-three-real-reviews-daily.yml
- 定时：cron 17 1 * * *（UTC），即北京时间约 09:17。
- 校验脚本：scripts/test_daily_product_reviews.py
- API 回归：scripts/test_daily_product_reviews_api.mjs
- 发布脚本：scripts/publish_daily_product_reviews.py

工作流执行顺序：

1. 校验 101 条来源记录、原始行号、型号与产品目录的一一对应关系。
2. 校验 5 个透明款型号别名、星级、作者、正文长度和 SHA-256 指纹。
3. 读取 D1 当天状态和永久账本。
4. 从未使用过的合格记录中安全随机抽取 1 条；不能按 Excel 前几行顺序发布。
5. 写入 D1 后核对 inserted 数量、当天数量、型号、来源行号和指纹。
6. 失败或响应不明确时，只读账本确认结果；严禁盲目再次 POST。

### 3.2 站长指定额外批次

额外批次不是常规定时任务。执行前必须：

1. 读取 D1 当天记录和永久账本。
2. 确认当天目标数量、已发布数量和剩余可用型号。
3. 只从真实 Excel 中随机选择未使用型号。
4. 执行对应批次的 dry-run，再进行一次正式写入。
5. 写入后重新读取 D1，逐条对比 sourceRow、sourceModel、model 和 sourceFingerprint。
6. 结果已存在时只核验，不重复写入；数量不符时停止并查明原因。

历史日期脚本仅用于对应日期的审计与恢复，不得直接复制日期后当作新日期的正式发布脚本。后续应逐步收敛为通用批次入口。

## 4. B2B 文章发布标准流程

### 4.1 内容准备

每个日期批次必须具备：

- 3 个不同 slug、不同采购场景的英文文章源文件。
- 每篇 7 个正文主题段落、10 条采购检查清单、4 组 FAQ。
- 每篇 3 个有真实 SKU 对应关系的产品链接说明。
- 每篇 3 篇人工挑选的相关阅读，不能自链，必须真实存在且主题互补。
- 每篇对应 ES、PT、RU、TR 四种完整译文；英文原文与四语正文都以 CMS 正式字段为准。
- 标题、段落、产品链接和 FAQ 必须与文章目标买家一致，不能三篇文章只替换行业名称而复用同一套内容。

对应源文件：

- data/blog-guides-YYYYMMDD-1.json
- data/blog-guides-YYYYMMDD-2.json
- data/blog-guides-YYYYMMDD-3.json
- data/blog-localized-copy-YYYYMMDD-1.json
- data/blog-localized-copy-YYYYMMDD-2.json
- data/blog-localized-copy-YYYYMMDD-3.json

### 4.2 图片准备与审核

每篇文章先完整读稿，再看最终图片。执行永久硬标准：

- 一篇一图，同批 3 张图片必须不同，不能只换裁剪或颜色。
- 1200×800、3:2 横版、WebP，文件大小 30–350 KB。
- 记录原始来源、文章 slug、行业场景、可见主体、场景契合理由和 SHA-256。
- 图片必须与目标买家、行业和采购场景直接相关；不能用通用水杯图凑数。
- 不得把示意图描述为真实客户、工厂、订单、认证或型号实拍。
- 五种语言的详情页、列表卡片和 OG 图必须使用同一篇审核通过的封面。
- 站长在 CMS 后台主动换图后，自动化必须尊重后台选择。

详细视觉标准继续遵守 BLOG_COVER_VISUAL_STANDARD.md；编辑标准继续遵守 BLOG_EDITORIAL_PUBLISH_CHECKLIST.md。

### 4.3 预检与正式写入

每个日期的准备脚本统一遵循以下顺序：

1. 获取最新 D1 快照：scripts/fetch_build_snapshot.py。
2. 生成该日期批次：scripts/prepare_blog_release_YYYYMMDD.py。
3. 运行图片 dry-run：scripts/publish_blog_images_YYYYMMDD_r2.py --dry-run。
4. 运行文章 dry-run：scripts/publish_blog_batch_YYYYMMDD_d1.py --dry-run。
5. 检查 payload 中恰好 3 篇文章、12 份四语译文、12 张本地化列表卡片；图片 manifest 必须恰好 3 张且 SHA 全部匹配。
6. 检查每篇文章的 3 个 SKU 链接、3 个相关阅读、7 个正文段落、4 个 FAQ，以及五语路径。
7. 文章、翻译与列表卡片通过通用 `/api/admin/blog-batch` 条件写入 D1；允许使用有效后台管理会话经 HTTPS API 直接提交，也允许受限 GitHub Actions 使用项目 CI 凭据提交。之后仍走主分支标准构建与线上验收。

正式写入顺序固定为：

1. 先上传 3 张审核通过的图片到 R2，并核对返回 URL、SHA-256 和 saved 状态。
2. 再通过专用管理员接口把英文文章、四语译文和列表卡片写入 D1。
3. 核对 D1 返回的 publishedSlugs、文章数量、翻译数量、列表卡片数量和 publishRevision。

不得读取或输出生产密钥。文章批量写入只能走通用 `/api/admin/blog-batch`：后台会话经 HTTPS API，或受限 GitHub Actions CI 凭据；禁止日期专用端点、浏览器操作和直接修改 dist。

### 4.4 Blog 默认静态页与显式动态备用入口验收

这是本次发布暴露出的关键架构差异，永久加入发布门禁：

- Blog 详情与列表默认由 D1 snapshot 静态构建；只有显式设置 XUYI_BLOG_RUNTIME_MODE=dynamic 时，functions/blog/[[path]].js 才从 D1 动态渲染。
- 所有后台标记为 enabled + publishReady 的语种页面都由同一份 D1 snapshot 与共享模板生成。
- 新日期的三篇文章必须同时进入动态 D1 渲染所需的 SOURCE_GUIDE_BY_SLUG 注册表；不能只进入静态构建数据。
- 每个新批次必须增加动态英文渲染回归测试，验证 3 篇文章均有 3 个相关阅读卡片、3 个 SKU 链接，并保留作者正文和询盘 CTA。
- 四语静态渲染也必须检查每篇 3 个相关阅读、3 个 SKU 链接和正确封面。

对应测试：

- scripts/test_blog_dynamic_evidence.mjs 与 scripts/test_blog_pagination_runtime.mjs
- scripts/test_contextual_share_metadata.py 与 scripts/test_owner_contextual_links_survive_rebuild.py
- scripts/test_localized_release.py
- scripts/test_localized_templates.py

如果某个日期的文章缺少动态渲染注册，必须在共享渲染器和测试中修复，不能只在构建后的 HTML 临时补卡片。

## 5. 正式发布与生产验收

正式发布必须由一次明确的 GitHub 主分支触发完成。一次批次只触发一次正式写入。

发布后固定执行：

1. 从 D1 重新获取最新快照。
2. 连续进行两次干净构建，每次都运行发布测试和 Blog/图片相关回归测试。
3. 部署 Cloudflare Pages，核对生产 build revision。
4. 由统一 workflow 执行线上 build-meta、详情页、列表、sitemap 和媒体回读。
5. 检查 15 个详情路由（3 篇 × 5 语言）。
6. 检查 15 次列表卡片出现情况（3 篇分别出现在 5 个语言列表中）。
7. 检查 3 张 R2 图片 HTTP 200、WebP MIME、文件大小与封面 URL。
8. 检查每篇 3 个产品链接、3 个相关阅读、发布日期和正确标题。
9. 检查 sitemap.xml HTTP 200，包含本批 3 篇文章。
10. 完成 IndexNow 提交；只报告“已提交”，不能宣称 Google/Bing 已经收录。

评价发布另行核对 D1 账本和对应产品详情页，不要把评价工作流的成功误当作文章已发布，也不要把文章工作流成功误当作评价已发布。

## 6. 失败处理与禁止事项

| 情况 | 正确处理 | 禁止做法 |
|---|---|---|
| R2 上传超时/响应不明 | 按 SHA 查询对象是否已存在，再决定是否重试 | 不核对就重复上传或换文件 |
| D1 写入超时/响应不明 | 重新读取 D1 账本/发布记录，确认是否已写入 | 盲目重复 POST |
| 英文页缺相关阅读 | 检查 D1 动态渲染器和来源注册表，补回归测试 | 只修 ES/PT/RU/TR 静态模板 |
| 某语言页面缺文章 | 检查翻译记录、路由和列表卡片 | 直接改线上 HTML |
| 构建失败但 D1/R2 已写入 | 保留已写数据，修复模板/测试后重新构建和部署 | 再次写入相同文章或评价 |
| 生产检查未通过 | 不宣布完成，修复后重新跑线上验收 | 以 CI 成功或 HTTP 200 单项代替完整验收 |

**触发纪律：**

- 不要连续提交多个相同发布触发词来“试试看”。
- 首次发布失败后，先判断失败发生在 R2、D1、构建、部署还是线上验收阶段。
- 如果 D1/R2 已写入，修复提交不得再次触发同一批次的正式写入步骤；只运行构建、部署和验证。
- 修复应落在正式数据源、共享模板或动态渲染器中，并新增回归测试。
- 任何人不得为了让 CI 变绿而跳过生产验收。

## 7. 每日完成记录模板

每天只需记录以下结果，后续不再重复描述整个技术过程：

- 日期（北京时间）：
- 评价：当天数量、型号、D1 账本核对结果、产品页显示结果。
- 文章：3 篇 slug、五语详情页 15/15、列表卡片 15/15。
- 图片：R2 3/3、SHA 与线上 URL 核验。
- 内链：每篇 SKU 链接 3/3、相关阅读 3/3。
- 构建：两次干净构建通过/失败。
- 部署：Pages 生产 revision。
- Sitemap / IndexNow：Sitemap 核验结果、IndexNow 提交结果。
- 异常：只记录具体失败环节、根因和永久修复文件；不得把临时绕过记为修复。

## 9. 后续维护原则

- 每日重复任务按本手册走，不再临时发明新流程。
- 新日期只更换日期批次的数据和审核素材；发布顺序、权限边界、质量门禁、回滚规则不变。
- 日期专用脚本逐步收敛为通用批次入口，避免复制粘贴脚本导致漏改日期、漏接工作流或遗漏测试。
- 任何标准调整先更新本手册，再更新代码和自动化测试；代码、手册、实际工作流必须保持一致。
