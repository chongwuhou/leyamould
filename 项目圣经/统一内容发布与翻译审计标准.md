# XUYI 统一内容、翻译与媒体发布标准

> **唯一执行入口：** 具体操作统一按 [XUYI 网站统一执行手册](docs/XUYI_OPERATIONAL_RUNBOOK_ZH.md)。本文件的原则优先级不变；带日期的历史说明仅供追溯。

生效日期：2026-11-05  
级别：P0，适用于人工、AI、localGPT、脚本、GitHub Actions、CMS 管理后台和后续所有自动化。

## 1. 先确定唯一真源

| 内容 | 唯一写入位置 | 禁止作为发布源 |
|---|---|---|
| 产品标题、H1、描述、OG、正文、翻译、博客、评价 | Cloudflare D1 / XUYI CMS 正式记录 | dist、线上 HTML、临时 JSON、一次性 HTML 替换 |
| 图片、封面、ALT 对应媒体 | Cloudflare R2；ALT 和引用关系写入 D1 | 直接替换网页图片地址、把本地文件当线上媒体 |
| 模板、组件、渲染器、回归测试、发布规则 | GitHub 源码 | 直接改生成页面 |
| dist、sitemap、静态页面 | 标准构建产物 | 手工修改后再发布 |

业务数据必须进入 D1；媒体必须先进入 R2，再由 D1 记录引用、ALT、语言和发布版本。源码模板可以在 GitHub 修改，但不能用源码里的临时内容绕过 D1 已有人工值。

## 2. AI 和工具的硬规则

- AI 只能做草稿、翻译初稿、SEO 组合建议、去重、格式整理、风险筛查和审计；不能凭空补造容量、材质、认证、MOQ、工厂证据、客户体验、评价或图片事实。
- AI 生成的产品、博客、翻译和评价，必须先进入“待审核”状态；审核通过后才能条件写入 D1。评价必须有可核验来源、准确 SKU、fingerprint、source 和审核状态。
- 工具默认只读或 dry-run。实际写入必须使用现有、已鉴权的 XUYI D1/CMS 或 R2 管理入口，并明确记录操作者、批次、时间、旧值摘要、新值摘要和 publish revision。
- 禁止脚本、插件、自动化或 AI 直接写 dist、线上 HTML、Cloudflare Pages 成品或 R2 缓存来冒充发布。禁止用旧静态回退表覆盖后台编辑。
- 工具必须幂等：重复运行不重复插入、不删除已有数据、不回退人工修改；更新必须按资源 ID、语言、SKU 和旧值/指纹条件写入。条件不满足就停止并报告，不强制覆盖。
- 任何计费、额度、试用赠金或费用不明确的 API 禁止使用；只用项目已批准且可确认安全的连接。

## 3. 产品、博客、评价和图片发布顺序

1. 读取 D1/CMS 当前记录、字段所有者和 publish revision，先做可恢复快照。
2. 读取真实产品/文章/评价来源，生成待审核草稿；翻译必须逐语言检查，不用英文正文自动充当译文。
3. 人工确认事实、SEO、五语、链接和图片场景。博客正文放 2–5 个真实相关产品链接，结尾人工选择 2–3 篇相关阅读。
4. 新图片先校验来源、尺寸、格式、SHA-256 和场景，再上传 R2 新对象；R2 成功后才写 D1 图片路径、ALT、语言和引用。原对象不覆盖、不删除，除非通过引用检查和可恢复流程。
5. 对 D1 做条件写入并 bump publish revision；失败或版本冲突时停止，不自动重试覆盖。
6. 由标准构建从 D1 + R2 + GitHub 模板生成 dist；必须完成两次干净构建、回归测试和 CMS owner-edit 保留测试。
7. 通过 CI 后才部署；部署后核对 build SHA、D1 revision、R2 对象、代表页面和 sitemap。失败停在 CI，不发布临时产物。

## 4. 已发布语种翻译审计门禁

当前生产基线为 EN、ES、PT、RU、TR；实际检查集合始终以 D1 `language_config` 中 `enabled + publishReady` 的语种为准。每个资源发布前必须检查：

- html lang、title、H1、meta description、OG、正文、导航、分类、按钮、ALT、FAQ、JSON-LD 的可见文案与目标语言一致。
- 不得出现整句英文回退、旧语言目录、英文面包屑、英文分类侧栏或“只翻标题不翻正文”。OEM、ODM、B2B、MOQ、SKU、ml、oz、FAQ 等行业缩写和型号可以保留。
- 每个语言 URL 的 canonical、hreflang、sitemap 和内部链接必须指向同语言已发布页面；缺翻译时不生成假翻译链接。
- 发生一条高置信度漏翻译，就阻止该资源批次发布，进入 D1/CMS 翻译队列；禁止在构建后替换 HTML 规避门禁。

2026-11-05 线上只读审计结果：sitemap 1,812 个 URL，HTTP 错误 0，五语 html lang 错误 0。发现并已在共享模板修复 24 个多语分类侧栏英文回退、4 个 About 面包屑 Home；另有 9 个博客多语正文/相关阅读含英文片段，属于 D1/CMS 内容，必须按本标准回写 D1 后再复核，不能直接改成品文件。FAQ、OEM/ODM 和 Email 等上下文词未自动判定为漏翻译。

## 5. SEO + GEO 内容可引用性标准（2026-11-10，永久执行）

本项目不把 GEO 视为一个单一、固定、公开的 AI 算法；GEO 的执行目标是让搜索引擎和 AI 系统能够理解、验证并引用页面内容。所有新写、重写或发布的产品、Blog、FAQ 和普通页面，必须先满足 SEO 基础，再按以下规则提高内容的可引用性。

### 标题、导航和页面结构

- 标题优先采用句子式、口语化、提问式表达，覆盖明确的长尾搜索意图和常见 FAQ；避免所有页面复用同一句营销标题。
- 页面导航清晰、层级扁平、分类和面包屑稳定；产品、分类、Blog、FAQ 和关键服务页之间保持真实、可理解的内部链接。
- H1、Title、Meta Description、正文、FAQ 和结构化数据必须相互一致，目标语言页面不能用英文内容冒充翻译。

### 内容深度、事实和证据

- 内容先直接回答问题，再解释参数、判断条件、操作步骤、适用范围和风险边界；避免“优质、领先、快速、专业”等没有证据的营销形容词。
- 优先使用参数清单、对比表、选型逻辑、决策树、检查表和 FAQ。标题示例可以是“液压油滤芯选型需要确认的 6 个参数”“原厂滤芯平替前必须核对的 5 个条件”，但实际数字必须与正文和来源一致。
- 可以写真实案例、实操过程图、数据验证、第三方测评、客户好评截图和实际使用场景，但必须有可核验来源、授权或明确的示意图声明。类似“能耗降低 30%”“交付周期 7 天”“通过 ISO 9001”等事实，只有在项目来源、D1/CMS 记录或可核验第三方资料支持时才能发布。
- 产品、品牌和厂家信息应在回答采购问题时自然出现，不为了品牌提及强行插入；产品参数、材质、容量、认证、MOQ、交期、工厂证据和客户关系不得由 AI 猜测。
- AI 可以提高研究、组织、翻译和审计效率，但不得批量生成无原创价值、空泛重复或未经核验的内容。每篇文章必须有独立问题、独立证据、独立采购场景和明确的读者下一步。

### 数据库、图片和外部平台

- 正文、Title、Meta、翻译、内链、FAQ、评价和产品数据仍必须写入 D1/CMS；图片先核验后进入 R2，再由 D1 保存路径、ALT、语言和引用关系。
- 图片优先使用真实产品/使用场景、操作过程图、对比图或清楚标注的示意图；不得用虚构客户、工厂、订单、测试或认证作为 AI 内容的“证据”。
- Reddit、Quora、YouTube、LinkedIn 和行业论坛属于后续分发渠道，不是默认发布源。获得明确授权后，按平台改写为问答、视频脚本、案例帖或专业帖子，不直接复制整篇文章群发；分发内容仍应回溯到网站 D1/CMS 的事实源，避免重复、误导和垃圾外链。

该标准适用于人工、AI、localGPT、脚本和 GitHub Actions。后续收到“发布文章”任务时，默认按本节执行，不再要求用户重复说明；若缺少来源证据，保留为待审核而不是补造事实发布。

## 6. 回滚和交接

- 文本回滚使用 D1 旧版本/快照或 CMS 审计记录；媒体回滚使用旧 R2 对象和 D1 引用恢复；源码回滚使用 Git 提交，禁止用旧 dist 覆盖现状。
- 每次发布交接必须写明：D1 表/资源/语言、R2 对象和 SHA、Git 提交、构建/部署 run、测试结果、线上核验 URL、是否存在待处理翻译。
- 未完成 D1/R2 写入、翻译审核、双构建或线上核验时，状态只能写“草稿/待审核/未发布”，不能写“已完成”。

本文件是产品、博客、评价、翻译、图片、SEO/GEO 和 AI/工具发布的统一操作标准；与历史脚本或旧说明冲突时，以本文件、AGENTS.md 和 PROJECT_CHANGE_POLICY.md 为准。

## 7. 2026-11-11 发布入口与后台维护收口

- Blog 批量发布只使用 `/api/admin/blog-batch` 一个通用入口。入口先读取 D1 `language_config`，以 `enabled + publishReady` 的语种集合生成翻译页和列表卡片网格；不得在接口或工作流里写死语种数量、日期接口或旧批次数量。
- 统一接口授权可使用有效的 XUYI 后台管理会话（HTTPS API 直接调用）或绑定本项目的 Cloudflare CI Token（GitHub Actions）；两种方式都进入同一套 D1 校验和冲突保护。AI 发布不操作浏览器，不使用日期专用写入端点。
- 批量重跑采用“已存在且完全相同则复用，已存在但内容不同则 409 停止”的条件策略。任何 D1 人工编辑都不能被旧批次覆盖；旧日期命名的批量 CI 写入口已经 fail-closed，只保留历史源码和离线回归资料。
- Blog 列表重排必须读取完整 D1 `published` 顺序，只调整每张完整卡片的位置；历史嵌套卡片可由共享解析器恢复，但禁止通过改线上 HTML 或 dist 解决。
- 定时发布的多语队列表不再使用固定语种 CHECK；初始化时会把旧表迁移到配置驱动结构。发布器检查 `locales.length`，不允许使用固定 `4` 或固定语种数组作为完成条件。
- 后台模块 06/产品 SEO/媒体 ALT 的语种选项、产品记录和数量均由 D1 API 返回；界面不得显示旧的“五语”“101 个产品”等事实性固定数字。批量导入的单次安全上限如果存在，必须明确标注为“单次批次上限”，不能冒充全站产品总数。
- 发布完成的最小回归集：全量 JS/Python 语法、preflight、P0 真源门禁、CMS owner 优先、Blog 列表单卡片与 D1 顺序、动态语种授权、语言切换 failover、代表 Blog 运行时和第二次干净构建。缺少 D1 snapshot 时，构建不得伪造成功；只能报告等待受鉴权快照。



## 8. Blog 默认静态发布与多语列表一致性（2026-11-11 定稿）

- 生产环境的 Blog 页面默认直接使用 Cloudflare Pages 静态构建结果；D1/CMS snapshot 是唯一内容源，英文和所有 `enabled + publishReady` 语种的 `/blog/` 列表均从同一份 `published blogPosts` 生成。
- 列表唯一排序为 D1 `ORDER BY updated_at DESC, slug ASC`。多语言输出只移动完整卡片并保留卡片 HTML，不按语言单独排序，不追加到末尾，不硬编码日期或批次 slug。
- `functions/blog/[[path]].js` 继续保留动态 D1 能力，但默认不接管页面；只有显式设置 `XUYI_BLOG_RUNTIME_MODE=dynamic` 才启用，并且必须沿用同一排序规则。看到该函数存在，不代表生产 Blog 默认动态读取。
- 发布门禁必须核验英文及所有发布就绪语种的卡片数量、slug 集合、顺序、单 H1、图片/正文/OG 一致性；任一异常停止发布。上线后还要核对代表语种的 HTTP、页面顺序和构建 SHA。

## 9. 日常发布固定操作规程（2026-11-12 起永久执行）

本节把前面的原则改成每天可以直接执行的固定路径。人工和 AI 使用同一套 D1/R2/CI 真源；区别只有“谁在后台录入”和“谁调用接口”。遇到历史日期脚本、旧批次入口或临时 HTML 修补时，一律回到本节。

### 9.1 人工发布路径

1. 先进入后台，读取 D1 当前语言配置、文章状态、产品/文章已有值和 publish revision。先确认 slug、目标语言和封面没有冲突。
2. 英文 Blog 文章在 Blog 内容发布模块完成：填写 Title、Meta Description、封面、正文、FAQ、采购清单、正文产品内链和文末相关阅读；先保存草稿，再人工审核事实和链接，最后点击发布。
3. 多语言文章在“内容与多语言 / 页面与 Blog 多语言”入口逐语种维护。每个 enabled + publishReady 语言都要有完整 Title、Meta Description、完整 Main HTML、封面 ALT 和本地化内链；不能只改标题，也不能把英文正文复制成翻译。
4. 图片先在 R2 媒体库完成上传和检查，再在 D1/CMS 保存 R2 路径、ALT、来源、SHA 和引用关系。后台主动选过的图片优先保留。
5. 保存后等待标准构建和线上核验。人工发布不直接编辑 dist、线上 HTML、浏览器开发者工具或 R2 缓存；发现错误回后台改正式字段，再重新构建。

### 9.2 AI 发布路径

1. AI 先读取项目圣经、D1 当前快照、语言配置、文章/产品/相关阅读和 R2 引用情况；先检查 slug 是否已存在，不能凭历史数量判断。
2. AI 生成英文草稿、各已发布语言译文、SEO 字段、FAQ、产品内链、相关阅读和图片审核记录。AI 只生成待审核内容，事实、型号、容量、材质、认证、MOQ、客户案例和图片场景必须有来源。
3. 图片完成真实视觉审核、尺寸/格式/SHA 校验后，先上传 R2；R2 成功后才能把媒体路径写入文章数据。
4. AI 发布只调用通用 POST /api/admin/blog-batch，使用已鉴权的 XUYI 后台会话或本项目 Cloudflare CI Token；不打开浏览器，不调用 Google API，不使用日期专用写入端点，不直接写 D1 REST、dist 或线上 HTML。
5. 请求体必须同时包含 posts、translations、indexCards。translations[].mainHtml 必须是完整文章页面 HTML，包含页面引导、唯一 H1、封面、目录、文章正文、FAQ、相关阅读和 CTA；不能把正文片段、Markdown 或仅文章主体当作 Main HTML。
6. 接口返回成功后记录 publish revision、写入条数和语言集合。接口返回 409、401、403、503 或结构校验错误时立即停止，保留现有 D1 值，不能重试覆盖或改用旧入口绕过。

### 9.3 两种路径都必须满足的内容门槛

- 正文 7 个实质章节，每章达到项目接口要求；10 条采购检查清单；4 个 FAQ；2–5 个不同且真实存在的产品详情内链；文末 2–3 篇人工选择的相关阅读。
- 英文和每个后台配置为 enabled + publishReady 的语言都要有完整详情页和列表卡片。语言数量、文章数量和产品数量只从 D1/config 读取。
- 封面为已审核的真实自然场景或明确标注的示意图；同批不重复；R2 先成功，D1 后保存引用。
- Title、H1、Meta Description、正文主题、FAQ、OG 和结构化数据保持同一搜索意图；标题可口语化、提问式、长尾化，但不堆砌关键词或虚构事实。

### 9.4 固定的发布顺序

读取 D1/CMS 快照 → 保存可恢复快照 → 生成/人工审核内容 → 核验 R2 → 通用接口条件写入 D1 → bump publish revision → 两次干净构建 → 全量回归 → 部署 → 核验线上详情页、列表顺序、canonical、hreflang、OG、sitemap 和 R2

任何一步失败都停在该步。不得用 dist、浏览器页面或一次性 HTML 替换跳过失败步骤。

### 9.5 固定失败处理

- 409：说明 D1 已有人工或其他任务修改，停止并重新读取当前值；不覆盖。
- 401/403/503：说明鉴权、绑定或服务状态异常，停止检查配置；不把密码或 Token 写入文章、仓库或聊天。
- 请求体结构错误：修正草稿/接口前置校验后重新生成；不把错误数据写入 D1。
- 构建或回归失败：状态记录为“D1 已写入、线上待发布”，修复正式模板/数据后重跑；不写临时静态页面，不重复插入文章。
- 线上核验失败：不宣称完成，保留可回滚的 D1/R2/Git 版本并报告具体 URL。

### 9.6 完成判定

只有同时满足以下条件才可以写“已发布”：D1/CMS 条件写入成功；所有配置语言的详情和列表数据齐全；R2 对象可访问；两次干净构建和 CI 门禁通过；部署成功；线上代表 URL 返回 200；标题、Meta、H1、FAQ、正文内链、列表 D1 顺序、canonical/hreflang、OG 和 sitemap 核验通过。

从下一次日常任务起，默认执行本节，不再重新研究历史脚本或重新设计发布流程。

## 10. 主题去重与关键词蚕食防止门禁（2026-11-17，永久执行）

本次全量盘点记录了现有 106 篇文章之间的主题重叠与关键词蚕食风险。**本次不删除、不合并、不改写现有文章，不改变任何既有 URL、slug、canonical 或发布日期。** 这批重叠仅作为后续内容策略和内链规划的基线，不能在后续发布中继续扩大。

### 新文章发布前的强制检查

1. 先读取 D1/CMS 当前已发布 Blog 的 slug、Title、H1、Meta Description、首段、章节标题、FAQ、产品内链、相关阅读和发布语种；不以记忆、固定数量或本地旧 JSON 代替当前数据库。
2. 给新文章登记一个唯一的主搜索意图，并标记内容角色：支柱页、选型/方法指南、产品/解决方案页或具体采购场景页。**一篇文章只能有一个主问题**，标题、H1、Meta、首段、章节、FAQ 和 CTA 必须围绕同一个问题。
3. 发布前做标题、主关键词、问题句、章节标题、FAQ 和首段的相似度/冲突检查。与既有文章覆盖同一采购问题、相同参数清单或相同决策路径时，不得仅换行业场景、颜色或形容词套壳发布。
4. 如果重叠，优先改变搜索意图、买家阶段、决策对象、证据类型或交付结果；必须增加新的信息增量，例如真实参数对比、采购表单、验收步骤、成本/交期边界、测试方法、案例来源或明确的适用/不适用条件。没有新证据就退回草稿。
5. 新文章必须选择与主意图互补的产品内链和相关阅读，避免同一组文章互相循环抢权重；相关阅读不能把高度同质化文章机械互链。
6. 对已有文章发现重叠时，本阶段只记录并停止新增冲突；不得自行删除、合并、改 URL、改发布日期或设置 301。未来如需整合，必须另行取得站长明确授权并先做流量、收录、内链和回滚评估。

### D1 主题登记与人工/AI统一流程

每篇准备发布的文章在 D1/CMS 草稿或发布审计记录中登记：`slug`、`intent`、`audience`、`funnelStage`、`primaryKeyword`、`coveredQuestions`、`evidenceSources`、`supportingLinks`、`canonicalRole` 和 `lastReviewed`。如果当前数据库没有独立字段，先在发布前审计记录/项目内容登记中保存，不允许用静态 HTML 代替。

人工和 AI 必须执行同一套门禁：读取当前 D1 → 建立主题地图 → 通过唯一主意图和信息增量检查 → 检查多语言是否围绕同一意图独立表达 → 再写入 D1。AI 可以协助相似度筛查和选题建议，但不能自行判定“换个标题就算新主题”，也不能绕过人工事实审核。任何一项冲突检查失败，保持草稿/待审核，不触发发布。

### 发布后复核

发布后记录新文章与相邻文章的主意图、关键词、内链关系和线上 URL；后续新增文章先更新主题地图，再进入写作。重复执行必须幂等，不能因为复核而新增副本或覆盖站长已编辑的字段。


## 13. D1 字段权威与构建输入边界（2026-11-18）

- Blog 正式内容的字段所有者是 D1 的 `xuyi_blog_posts.content_json`。采购决策表使用 `buyerDecisionTable` 字段；后台人工编辑、通用 Blog API 和 AI/API 批量发布都必须写入这个字段，静态构建只读取 D1 snapshot 中的生效值。
- 产品 Title、Meta Description 和 OG 的最终值由 D1 的 `xuyi_product_seo` 按 `slug + locale` 管理。历史 SEO 刷新清单只能作为一次性审计记录，不能继续成为构建输入。
- 任何带日期的批次 JSON、临时 payload 或一次性迁移脚本完成任务后必须从正式构建路径移除；需要历史依据时保留在 Git 审计记录或专用测试 fixture，不得让渲染器直接读取它们。
- 永久门禁必须从构建 snapshot 检查：所有当前源 Blog slug 对应的已发布 D1 行存在、`buyerDecisionTable` 结构完整；缺失时构建失败，不允许静默回退到旧批次文件。
- 迁移采用“只补缺失、已有值冲突即停止、条件更新、幂等、成功后 bump revision”。迁移完成后删除一次性入口；后续人工和 AI 统一回到正常 D1/CMS 发布入口。
- 这套规则不依赖当前产品数量、语言数量或文章数量，均以 D1/config 当前快照为准。
